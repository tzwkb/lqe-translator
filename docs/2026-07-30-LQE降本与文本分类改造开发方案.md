# LQE 降本与文本分类改造开发方案

## 1. 基本信息

| 项目 | 内容 |
|---|---|
| 讨论日期 | 2026-07-30 |
| 目标仓库 | `Langlobal/lqe-translator` |
| 基线分支 | `main` |
| 基线提交 | `925ba6f` |
| 文档状态 | 已实现并通过回归 |
| 主要目标 | 减少不必要的建议译文和冗长说明，并利用上游文本分类调整检查重点 |

本方案记录今天确认的需求、与现有 LQE 合同的对齐结果、实际实现和验收结果。

## 2. 今日需求

1. Critical、Major 问题必须保留问题说明；是否提供建议译文仍由 Agent 根据能否可靠修改进行判断。
2. Minor 问题只保留问题说明，不生成局部 edit、corrected 或完整建议译文。
3. 将 20–30 字符作为问题说明的提示词软目标，完整说明优先，不增加硬校验。
4. 文本分类由上游提供。LQE 不自行分类，只在输入存在文本分类时按分类规则调整检查重点。
5. 文本类型规则必须映射到现有 LQE 模块和错误类别，不新增一套平行检查维度。

## 3. 现有系统事实

### 3.1 正式检查结构

标准模式的必需 AI 模块为：

| 模块 | 正式错误类别 |
|---|---|
| `terminology` | Terminology、Inconsistency、Company style，以及机器预检复核 |
| `accuracy` | Mistranslation、Omission、Addition、Untranslated |
| `grammar` | Grammar、Spelling、Punctuation |
| `naturalness` | Audience appropriateness、Culture specific reference、Unidiomatic |

无术语模式使用 `precheck_review` 替代 `terminology`，并继续运行 `accuracy`、`grammar` 和 `naturalness`。`proper_names` 只用于术语表自检，不参与普通文本类型路由。

机器预检负责变量、标签、换行、数字、长度、空格、部分标点、文件内一致性及项目自定义确定性规则。文本分类不能关闭机器预检。

### 3.2 问题与建议是两个合同

正式 issue 字段为：

```json
{
  "category": "Grammar",
  "severity": "Minor",
  "comment": "The verb form is incorrect.",
  "needs_confirmation": false,
  "edit": {
    "from": "are",
    "to": "is",
    "evidence": null
  }
}
```

其中：

- `comment` 是英文问题说明，当前已要求非空。
- `edit` 是经过脚本验证后才能应用的安全局部修改。
- `corrected` 由脚本根据有效局部 edit 生成，不由模型直接提交。
- `reference_suggestions.json` 保存报告专用完整参考译文，不进入 corrected 或自动应用流程。

因此，“Minor 不给建议译文”必须明确是只关闭完整参考译文，还是连安全局部 edit、corrected 展示和自动迭代也一起关闭。两种含义会产生不同交付结果，不能在实现时自行推断。

### 3.3 已有文本类型数据链路

表格输入已经自动识别以下列名：

```text
content_type
text_type
文本类型
文本类别
```

当前数据链路已经保留：

```text
输入分类列
→ state.segments[].content_type
→ chunks[].segments[].content_type
→ review packet
→ reference suggestion packet
```

另外，历史 AIPE 格式中的文本类型标记行会写入 `text_type_context`。本次不需要开发分类模型或额外分类调用。

## 4. 需求与现有 LQE 结构的归一化

原始业务维度不能直接写进提示词，应先归入正式模块：

| 业务说法 | LQE 实际归属 |
|---|---|
| 拼写 | `grammar` → Spelling |
| 标签 | 机器预检 → Markup |
| 长度、变量、换行和格式约束 | 机器预检 → Length、Markup、Locale convention、Other |
| 术语 | `terminology` → Terminology、Inconsistency |
| 准确性 | `accuracy` → Mistranslation、Omission、Addition、Untranslated |
| 地道性 | `naturalness` → Unidiomatic |
| 明确风格指南违规 | `terminology` → Company style |
| 角色声音、语域和受众适配 | `naturalness` → Audience appropriateness |
| 文化问题 | `naturalness` → Culture specific reference |
| 数字机械不一致 | 机器预检 |
| 数字、条件或机制含义错误 | `accuracy` |

“基础级、标准级、高级”不是当前 LQE 的正式字段。本次不新增该抽象，直接对现有模块设置检查强度。

## 5. Minor 降本例外与建议判断

### 5.1 已确认规则

| 严重度 | 问题说明 `comment` | 局部 `edit` | 完整参考建议 |
|---|---|---|---|
| Critical | 必须非空 | 由 Agent 按现有安全合同判断 | 由 Agent 判断能否可靠生成 |
| Major | 必须非空 | 由 Agent 按现有安全合同判断 | 由 Agent 判断能否可靠生成 |
| Minor | 必须非空 | 固定为 `null` | 不进入完整参考建议生成 |
| Neutral | 必须非空 | 按现有合同 | 默认不进入完整参考建议生成 |

严重度表示问题影响，不表示 Agent 一定能够生成可靠建议译文。段内只要存在一个 Critical 或 Major issue，该段即具备完整参考建议资格，但最终是否提交建议仍由 Agent 判断。混合严重度段只进入一次 suggestion packet，但 packet 只向建议 worker 提供 Critical/Major issue；Minor issue 仍只在报告中保留问题说明。

Minor 是本轮为降本增加的单向例外：即使 Agent 能够可靠修改，也不生成 `edit`、corrected 或完整参考建议。Critical/Major 不增加强制覆盖要求，继续沿用现有可靠性判断。

### 5.2 推荐生成顺序

```text
模块检查
→ 合并并验证局部 edit
→ 生成 corrected
→ 筛选含 Critical/Major 的未解决段
→ 生成报告专用完整参考译文
→ 写报告
```

如果有效 corrected 已经完整解决该段的 Critical/Major 问题，不重复生成完整参考译文。存在以下情况时允许不生成完整建议，但必须保留问题说明并显示需人工处理：

- 段或文本受保护。
- 上下文不足。
- 存在多个合理方案。
- 建议会破坏变量、标签、换行或受保护文本。
- 无法可靠保持原意。

### 5.3 建议候选筛选合同改动

当前 `lqe_suggestions.py` 只能按类别和 `only_missing` 筛选。建议增加严重度筛选，用于排除 Minor，而不是强制 Critical/Major 生成建议：

```bash
python "$SCRIPTS/lqe_suggestions.py" prepare \
  --job "$JOB" \
  --severities "Major,Critical" \
  --only-missing
```

建议 selection 增加：

```json
{
  "categories": [],
  "severities": ["Critical", "Major"],
  "only_missing": true
}
```

新 packet、draft 和 artifact 继续绑定 selection、结果摘要和 generation。进入 packet 只代表允许 Agent 生成建议，不代表必须提交建议。本次已将 suggestion packet、draft 和 artifact 升级到 version 2；version 1 明确拒绝并要求重新 prepare、publish，避免新旧 selection 合同混用。

## 6. Minor 只报告问题

D1 已确认采用原方案 C：

- Minor issue 仍使用固定 issue 接口。
- `category`、`severity` 和非空 `comment` 正常输出。
- `needs_confirmation` 固定为 `true`。
- `edit` 固定为 `null`。
- Minor-only 段不进入 `reference_suggestions` worker。
- Minor 不生成 corrected，也不参与自动迭代修复。
- 报告保留错误类别、严重度和问题说明，“AI/建议译文”保持空白。

这样同时减少局部 edit 和完整参考重译的输出 token。publisher 应拒绝 Minor 携带非空 edit，不能只依赖提示词。

混合严重度段按 issue 分流：Critical/Major 仍可生成 edit 或完整参考译文；同段 Minor 只保留问题说明，不作为建议 worker 的改写要求。

## 7. 问题说明长度软目标

### 7.1 当前约束

`comment` 当前要求：

- 英文。
- 非空。
- 简短说明问题，可引用少量原文或译文。

当前没有字符上限。

### 7.2 已确认策略

在检查模块提示词中加入以下软目标：

```text
Keep the English comment concise, preferably 20–30 characters.
Completeness and clarity take priority; do not pad or truncate mechanically.
```

20–30 字符不是合法性范围，也不是 publisher 上限：

- 少于 20 字符但信息完整时允许。
- 超过 30 字符但为说明对象、原因或影响所必需时允许。
- 不为满足下限补充无效措辞。
- 不为满足上限截断信息。

字符统计按去除首尾空白后的 Unicode 字符计算，空格和标点计入。该规则只加入提示词并观察效果，不在 publisher 中硬失败。

原因：

- 当前 comment 为英文，20–30 字符较严格。
- 直接硬失败会因说明略长导致整批发布失败。
- 软目标可减少输出，同时保留说明完整性。

### 7.3 评估指标

评估时至少记录：

- comment 平均值、中位数、P95 和超限比例。
- 人工一次读懂比例。
- 需要重新查看原译才能理解问题的比例。
- 说明与 category 重复、缺少对象或缺少原因的比例。
- 每个 issue 的平均输出字符数。
- 首轮结果与格式重试结果，二者分开统计。

本轮不在 `issue_contract_problem()` 增加长度验证。

## 8. 文本类型差异化检查

### 8.1 数据使用规则

每段按以下顺序确定文本类型：

1. 使用非空的行级 `content_type`。
2. 否则使用继承的 `text_type_context`。
3. 两者都为空或值无法识别时，按全部模块“标准”强度处理。

LQE 不得根据原文、文件名、工作表名或目录名推断文本类型。上游分类值原样保留，分类规则只影响检查重点，不改写输入值。

### 8.2 强度定义

| 强度 | Agent 行为 |
|---|---|
| 重点 | 主动检查本模块全部负责类别，包括语境相关和细微但实质的问题 |
| 标准 | 检查明确、可说明的问题，不做偏好型或润色型挑错 |
| 保底 | 不主动追求 Minor 润色，只报告影响功能、理解或达到 Major/Critical 的明显问题 |

任何分类都不能压制明显 Critical/Major。分类不改变：

- 模块类别所有权。
- 严重度定义和评分。
- `state.check_scope`。
- 机器预检。
- 术语确认与保护规则。
- TM 和受保护段规则。

### 8.3 LQE 模块强度矩阵

| 文本类型 | `terminology` | `accuracy` | `grammar` | `naturalness` |
|---|---:|---:|---:|---:|
| UI/界面文本 | 重点 | 重点 | 重点 | 保底 |
| 技能/道具描述 | 重点 | 重点 | 标准 | 标准 |
| 主线剧情对话 | 重点 | 重点 | 重点 | 重点 |
| 支线/NPC对话 | 标准 | 重点 | 重点 | 重点 |
| 系统提示/教程 | 重点 | 重点 | 重点 | 标准 |
| 世界观/背景文本 | 重点 | 重点 | 重点 | 重点 |
| 战斗/操作提示 | 重点 | 重点 | 标准 | 标准 |

无术语模式不得借文本类型重新启用 `terminology`。`precheck_review` 仍只复核已有非术语预检问题。

### 8.4 提示词落点

共享规则应写入：

```text
references/check_modules/common.md
```

所有必需模块 worker 已在每个批次开始时读取该文件，因此无需在四个模块文件中重复整张矩阵。各模块只读取矩阵中自己的列。

完整参考译文生成还应在以下文件增加一条规则：

```text
references/suggestions.md
```

建议 worker 应使用 `content_type` 或 `text_type_context` 调整语气、简洁度、角色声音和技术文本表达，但不得改变 issue、严重度或保护合同。

## 9. 成本影响

### 9.1 本轮能够节省的成本

- Minor 不生成局部 edit、corrected 或完整参考译文；Neutral 默认不进入完整参考译文 worker。
- 机器预检发现 Minor 时同样移除局部 edit，避免 corrected 和自动迭代绕过该规则。
- Critical/Major 已有完整有效 corrected 时不重复重写。
- comment 变短，减少输出 token。
- 技术文本的自然度模块不再进行润色型扩写。

### 9.2 本轮不能节省的成本

当前 `lqe_review.py prepare` 仍会把所有可审段发送给当前 scope 的四个必需模块。只修改提示词和检查强度不会显著减少输入 token。

如果后续需要进一步降本，应单独设计“按文本类型裁剪 module packet”的第二阶段改造。该改造会改变正式覆盖和 auto-publish 合同，不属于本轮范围。

## 11. 测试计划

### 11.1 严重度与建议

- Critical-only 段进入 suggestion packet。
- Major-only 段进入 suggestion packet。
- Minor-only 和 Neutral-only 段不进入 suggestion packet。
- Critical/Major 是否实际提交完整建议仍由 Agent 按可靠性判断，不要求全量覆盖。
- 每个 Minor issue 必须为 `needs_confirmation: true`、`edit: null`。
- publisher 拒绝 Minor 携带局部 edit。
- Major + Minor 混合段只进入一次，suggestion packet 只携带 Major issue。
- 已有完整有效 corrected 的 Critical/Major 段在 `--only-missing` 下不重复进入。
- 受保护段不进入。
- 变量、标签、换行和 `protected_texts` 变化仍被拒绝。
- 所有严重度的 comment 为空时继续失败。

### 11.2 文本类型

- 四种支持的分类列名均能被识别。
- 行级 `content_type` 优先于 `text_type_context`。
- 分类值进入四个 review packet 和 suggestion packet。
- 分类为空或未知时按标准强度，不自行推断。
- no-terminology 模式不会因分类值启用术语模块。
- 机器预检结果不因分类而减少。

### 11.3 comment 长度软目标

- 对比当前基线与加入 20–30 字符软目标后的输出。
- 统计长度分布、可理解度和输出量。
- 验证少于 20 或超过 30 字符的完整说明仍可正常发布。
- publisher 继续只校验 comment 为非空字符串。

## 12. 验收标准

满足以下条件后才能发布：

1. 所有 issue 仍具有合法 category、severity 和非空 comment。
2. 完整参考建议只面向含 Critical/Major 的合格段。
3. Minor-only 段只显示问题信息，不产生建议译文、corrected 或迭代修改。
4. 文本分类缺失或未知不会缩小现有检查范围。
5. 文本分类不会绕过机器预检、scope、术语保护或受保护段。
6. 现有报告合同、artifact digest 和 generation 绑定保持有效。
7. comment 长度试验报告区分首轮数据和格式重试数据。
8. 完整回归测试通过。
9. 仓库版本与安装目录版本同步后分别验证。

## 15. 2026-07-31 追加：运行模式开关

为避免四项降本规则永久覆盖完整审校行为，新增 job 级双模式开关。第 12 节的验收标准适用于 `optimized`；`full` 恢复降本改造前的输出行为。

| 模式 | Minor 局部修改 | comment 目标 | 完整建议候选 | 文本分类规则 |
|---|---|---|---|---|
| `optimized`（降本） | 禁止 | 20–30 字符软目标 | Major/Critical | 启用分类矩阵 |
| `full`（完整） | Agent 判断安全性 | 无字符目标 | Neutral/Minor/Major/Critical | 分类仅作上下文 |

Agent 在新任务执行 `read` 前必须先询问用户选择；用户已在当前请求中明确选择时不重复询问。CLI 使用 `--review-mode optimized|full`，解析结果写入 `state.review_policy`。兼容旧的直接 CLI 调用时，省略参数按 `optimized` 处理；这不是 Agent 跳过询问的授权。

模式是 job 合同，不是临时提示词：

1. `review_policy` 进入 state fingerprint、chunk、review packet 和 suggestion packet。
2. publisher、Minor edit 校验、corrected 构建、预检、报告和 suggestion selection 都读取同一策略。
3. 已有 job 直接沿用 `state.review_policy`；中途改变策略会使旧 generation 和 packet 失效，必须重新初始化或重建。
4. 缺少 `review_policy` 的历史 state 按 `optimized` 兼容，保持开关上线前的当前行为。
5. suggestion packet、draft、artifact 升级到 version 3；旧 artifact 必须重新 prepare 和 publish。

追加验证结果：仓库 `449` 个单元测试通过，原生测试 `159/159` 通过；安装目录的开关专项测试与原生测试同样通过。
